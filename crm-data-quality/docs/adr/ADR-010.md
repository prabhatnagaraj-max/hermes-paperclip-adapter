# ADR-010: Observability and Operational Readiness Baseline

## Status
Accepted

## Context
The integration must be supportable from day one. Without minimum telemetry standards, failures in auth, sync, or scoring are hard to isolate quickly.

This is a pre-environment decision and defines the baseline to implement once environment-specific telemetry sinks are selected.

## Decision
Define baseline observability for v1: structured logs, correlation IDs across extract/score/publish stages, and core metrics (latency, throughput, failure classes, retry counts).

## Consequences
- Positive: Faster incident triage and safer rollout decisions.
- Positive: Enables objective SLO tracking for integration reliability.
- Negative: Additional implementation and dashboard setup effort.
- Negative: Telemetry schema drift must be governed.

## Alternatives Considered
- Best-effort logging only: rejected due to weak diagnostics.
- Heavy observability platform integration in v1: rejected to keep initial scope lean.

## Open Risks
- Correlation ID propagation may be inconsistent across adapters unless enforced by shared middleware contracts.
- Metric cardinality can grow unexpectedly if tenant/environment dimensions are unconstrained.
- Alert thresholds may be noisy before baseline volume patterns are established.

## Follow-up Decisions
- Decide authoritative telemetry schema owner and review cadence before first production rollout.
- Confirm metric retention windows and cost guardrails per environment tier (Dev/Test/Prod).
- Finalize on-call escalation path and incident-response runbook linkage for CRM-DQ alerts.
